# tools/usb-probe

Read-only Windows PowerShell 5.1 scripts for the hardware experiments: the E1 probes (USB identification of the
SmartFade 1248). They never write to the console: no output reports, no feature reports, no
bulk traffic.

| Script | What it prints | Mechanism |
|---|---|---|
| `e1-usb-descriptors.ps1` | For the device with VID 0x14D5 on any hub: connection info (speed, address, open pipes), device descriptor, string descriptors, the full configuration descriptor (interfaces, HID descriptor, endpoints), and an attempt at the HID report descriptor | Standard GET_DESCRIPTOR requests routed through the parent hub driver (`IOCTL_USB_GET_DESCRIPTOR_FROM_NODE_CONNECTION`), the same mechanism USBView / USBTreeView use |
| `e1-hid-probe.ps1` | For the console's HID collection: `HIDD_ATTRIBUTES`, manufacturer / product / serial strings, `HIDP_CAPS`, link collections, value and button caps (the report structure Windows parsed), then a passive listen for input reports for `-ListenSeconds` seconds | HID class driver (`hid.dll` `HidD_*` / `HidP_*` queries, `ReadFile` on the interrupt IN pipe) |
| `action-log.ps1` | Operator action log for capture sessions: type a note and press Enter at the moment of each action; every line is stamped with the PC clock (the clock USBPcap uses), so frames can be correlated with actions. Ends on an empty line. Refuses to append to an existing file (logs are hashed evidence) | Plain file writes; never touches the console |
| `e9b-guided-session.ps1` | Guided operator session for E9b, the repeat of E9 (2026-10-31): the open questions of E9 asked first, the same gate and SmartSoft start, E9's live Simulator steps again for a second session, then the tests of H81 (a PC fader against the physical fader), H82 (STACK, IND 1, IND 2, FADERS 25-48 from the Simulator), H83 (the console's own EDIT MEM selection on pages 1 and 12), H84 (the label with a caron across two SmartSoft restarts), H85 / H86 (REC MEM with the MASTER at half, deletion by REC MEM of an empty look) and, optionally, a cell edit in the Mem Edit tab; memory 9 of page 1 is recorded and deleted again. Our software is not involved | Plain file writes and Start-Process of SmartSoft; never touches the console itself |
| `e12-guided-session.ps1` | Guided operator session for E12 (planned 2026-10-31; run with it the same afternoon and analysed that evening, record `docs/protocol/captures/2026-10-31-e12-smartsoft-patch-stack-edits.md`): SmartSoft Online edits the patch (channel 47 to DMX 100, IND 1 to DMX 101, optionally the IND panel), the stack (a cue inserted after the last one and a point cue, its times and label, optionally a Direct cue), the KOTLIK sequence (a step inserted, a time, the run mode, the label), memory 9's content and name and optionally page 12's name, with the owner's decisions asked first, a SmartSoft restart to read the console's stored bodies back, optionally the console's own patch and step-timing menus, every change restored (moves and deletes included) and a second restart as the check; the show is backed up to the SD card before and saved again after for a byte comparison. | `e12b-guided-session.ps1` | Guided operator session for E12b, the second, independent SmartSoft session after a console power cycle (planned 2026-10-31, evening; trimmed the same evening at the owner's request to what is still needed, about 30 minutes; not run). The same safety frame as E12 (a named SD backup first, ETC's driver on interface 1, USBPcap before SmartSoft into an absolute path, every change restored, an after-session SD save to compare) around: one Patch drag (channel 47 to DMX 100) and its un-patch, the IND 1 panel with the values named by the owner before and after each change, a Direct cue inserted with channel fader 5 at half and labelled with a "č" and a full third line, a channel step (channel 47) with one time edit, a point cue later moved and deleted, inserts at step 3 and at the end of KOTLIK, One Shot then Manual, page 12's name, an SD save of the EDITED show, one SmartSoft restart for the console's stored bodies, and (optional H) the console's own Step Timing on the Direct cue and its Insert / Delete step menus in the stack and in KOTLIK. Memory 9 and the Mem Edit, memory-name and console REC MEM steps of E12 are not repeated (VERIFIED already); the steps reference memory 01/01. E12's lessons built in: no looks outside the steps (a look is a write), no memory-step label, the right-clicked row and the landing place logged, a "did you click anything else" question after each section, the console back in channel mode at the end. Run from the repository root: `powershell -NoProfile -ExecutionPolicy Bypass -File tools\usb-probe\e12b-guided-session.ps1 -LogFile e12b-actions.txt` | Passive: SmartSoft sends, our software is not involved; the owner's decisions are asked first |
| `e11-guided-session.ps1` | Guided operator session for E11, the first live-control session of our own software (SC-2 classes A and B1 as the owner implemented them; written 2026-10-31, evening; **attempt 1 run 2026-11-01, morning: no write sent**, see `docs/protocol/captures/2026-11-01-e11-first-live-control-session-attempt-1.md`; corrected the same day for attempt 2). Refuses to start unless the SC-2 re-check's open items are closed and every written acceptance SC-2 lists is given (H66 unknown, last mover, lost release, live output, the two review points, the rig decision); then the SD backup gate and the versions (backend commit, Windows build, firmware, cable), USBPcap before the Zadig bind into a new file per attempt (`e11-yyyyMMdd-HHmm.pcap`, an absolute path), the INCOMPLETE-WRITE.txt check, the backend with `--Device:Usb:LiveControlDate=<today>` and the UI, the HARDWARE + LIVE CONTROL badge check, Connect and a read-only minute, **W0: the console made to report its state from the panel** (FADERS MEMS, FADERS 1-24, SOLO on and off, the MASTER down and back; attempt 1 showed that a console with nothing pending reports nothing, F166, and every control is then refused by design), then one control at a time with 10 s between and the console's answer asked after each (channel fader 1 with a three-case answer: a refusal is "not sent" and repeats W0 once, a sent event the console does not follow is the H66 stop; bump 7, SOLO, BLACKOUT, BUMPS, optionally FADERS MEMS / memory bump 1 / FADERS 1-24 from the UI, MASTER last, optionally GO with STACK unlit), no SD save or load while connected (F163), Disconnect at an idle point, the end-of-session report, the SD save to compare. **Attempt 2 (2026-11-01, afternoon): four class-A fader events sent and followed by the console; the session ended on the W1 question when the owner typed the case letter "b" for the followed case, so the guide now accepts a / b / c and confirms before an H66 stop. Low risk: live state only, no show data on purpose; the after-session SD save checks it |
| `e9-guided-session.ps1` | Guided operator session for E9 (the passive USBPcap capture of SmartSoft writing): the safety-rule-3 gate, the check that interface 1 is back on ETC's driver (service ETCHSP) and a Memory Integrity reading, SmartSoft started by the script after USBPcap runs, then one instruction at a time (Console Simulator fader, bump, MASTER, BUMPS, BLACKOUT, SOLO, a memory bump, GO with STACK unlit, the Playback tab's all-faders-to-zero, a label with a caron, an optional Mem Edit, and REC MEM / EDIT MEM / COPY through the Simulator keys on the empty memories 9 and 10 of page 1, deleted again at the end) with the PC-clock time of each action and the owner's answers. Run without installation or admin rights:

```
powershell -NoProfile -ExecutionPolicy Bypass -File tools\usb-probe\e1-usb-descriptors.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tools\usb-probe\e1-hid-probe.ps1 -ListenSeconds 30
```

Output is evidence: copy it unmodified (plus a one-line header with date, host and script)
to `docs/protocol/captures/` with a date prefix and reference it from the experiment record.

**Rule:** these tools never send HID output or feature reports, bulk data or vendor requests,
and nobody adds such a feature here. An enabling or control message may only be reproduced
after it has been observed from SmartSoft (not from the firmware updater `SFDownloader.exe`)
in a capture and is understood. Both scripts were revised after the 2026-10-28 safety review
(hub opened with access 0 instead of GENERIC_WRITE; report grouping by the console's first byte
and all reports printed); the experiment record lists the hashes of the revisions used.

Limitations seen on 2026-10-28: string descriptors and the HID report descriptor could not be
read through the hub IOCTL (ERROR_GEN_FAILURE). Strings come from the HID path instead, and the
report structure is reconstructed from Windows' preparsed data, not from the raw descriptor.
