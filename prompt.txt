SmartFace 1248 Control Software — Project Brief
You are working on a software project whose goal is to build a modern replacement/alternative control application for a SmartFace 1248 lighting console.

The existing application used with the console is SmartSoft. The goal is NOT necessarily to clone SmartSoft's UI. The goal is to build our own software that can communicate with and control the physical SmartFace 1248 in a reliable way.

The project should be designed so that the hardware communication/protocol layer is completely separated from the UI and application logic.

1. Primary Goal
Build a desktop application that allows a user to control and monitor a SmartFace 1248 from a PC.

Conceptually:

┌──────────────────────────────────────────┐
│              Angular UI                  │

Do not invent or assume the SmartFace protocol.

Potential desktop technologies such as WebView2 or Tauri can be evaluated later.

For the initial implementation, prioritize a clean architecture and easy development/debugging.

5. Critical Architectural Principle
The most important architectural requirement is:

The UI must NOT know how the SmartFace communicates.
For example, Angular should never contain code like:

serialPort.write(...)

or:

midi.send(...)

or SmartFace-specific binary protocol code.

Instead:

Angular
   │
   │ "Set channel 12 to 75%"
   ▼
Application API
   │
   ▼
SmartFace application layer
   │
   ▼
SmartFace protocol
   │
   ▼
Communication transport
   │
   ▼
Hardware

The frontend should deal with domain concepts.

Examples:

setChannelLevel(channel: number, level: number)
recordCue(cueNumber: number)
executeCue(cueNumber: number)
setGrandMaster(level: number)

It should NOT deal with:

0x01 0x7F 0x0C 0x4B ...

Those details belong in the protocol layer.

26. Safety
The software controls physical lighting equipment.

Therefore:

Never invent commands.

Never send unverified binary data to the real console.

Provide a simulation/mock mode.

Clearly distinguish simulation from real hardware.

Make connection status obvious.

Avoid automatic execution of potentially destructive commands.

Require explicit user action for operations such as reset/clear if applicable.

Implement safe disconnect behavior.

During protocol development, default to MOCK mode.

Only enable REAL HARDWARE mode deliberately.
